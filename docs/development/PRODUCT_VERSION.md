## Release policy and explicit bump procedure

The single product identity source is `eng/ProductRelease.props`: `OtoProductVersion=0.1.0`, `OtoChannel=Pengembangan`. Desktop assembly embeds both values; product-info.json is emitted by the same build properties. Packaging checks the DLL informational version against product-info before emitting product/channel into build-info, manifest and latest/current pointer metadata. Existing `Version` fields remain immutable timestamp+hash package IDs for compatibility. No global replacement of build ID fields.

Product version changes only for an intentionally published product release with explicit user decision. Patch (0.1.1): bug/small/UI change. Minor (0.2.0, patch reset): new feature. Stable first release is 1.0.0 only after required gate/sign-off; subsequent major bumps mean major/breaking changes, not every stable release. Ordinary builds/tasks must not bump the product version. Multiple packages may legitimately retain 0.1.0; updater ordering/integrity/rollback continue using build IDs.

Procedure: record the requested release/bump decision here; edit only the product/channel properties in ProductRelease.props; update explicit version expectations in ProductVersionChecks/About audit; run product/updater/native UI checks and standard Build-LocalUpdate gates. Review resulting binary, product-info, build-info, manifest/latest agreement before release. Never relabel an old package or alter an installed immutable version.

About and Settings read embedded metadata from the running binary. Technical detail/copy also include full running build ID. Available local identity comes from hash-verified package build-info; staged identity comes from the exact installed version directory specified by the completion flow, not current/latest for running identity. Missing/invalid legacy product metadata explicitly says “Versi produk belum tercatat · Build <id>”. Two builds with the same product version show “Pembaruan build untuk versi produk yang sama”. Restart handshake, package paths, timestamps, SHA256 and previous pointers keep build IDs. Online metadata accepts optional productVersion and keeps existing development channel wire contract; old server feeds fall back transparently. No remote publication is performed by this task.
